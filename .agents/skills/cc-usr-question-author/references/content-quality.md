# 题目与快照内容要求

## User Prompt

User Prompt 是交给开发者的一段真实需求，不是出题模板。正文必须使用自然、克制的中文书面语，并在同一段中交代业务处境、需要解决的问题、关键边界和可观察的验收结果。技术名词、协议名、代码标识符可以保留英文，除此之外不要用中英文逐句对照。

先从这道题独有的业务矛盾或使用场景起笔，再按事情本身的因果关系展开。不要以“从零构建一套”“请实现以下功能”等批量出题常用句开头；不要使用“背景：”“功能：”“技术：”“验收：”标签、标题、编号清单或相同的收尾句。不同题目不能只替换业务名词、技术栈和状态名后沿用同一语序。

需求中只出现使用者真正会关心的产品行为。不得提及数据生产、评测、标注、目标模型、满意度、题目难度、预期得分、轨迹、质检或“为了测试能力”等内部目的。验收标准写成可观察的业务结果，不写给评分人员看的提示。

### 人类语言与反模板硬门槛

每个批次都必须先做人工句式审阅，再导入 SQLite。批次中至少安排三种不同的叙事起点（例如一线人员的异常、用户投诉后的追查、运营决策的取舍），并打散需求展开顺序；不能把“请搭建/实现一个 Go 服务”接一串固定的接口、状态、幂等、持久化和测试要求作为默认骨架。去掉业务名词、技术名词和字段名后，若两题仍保留相同的四段以上请求顺序，或共享可直接复制的验收尾句，必须重写。

重写要改变真实说话人的关注点和因果叙述，而不是替换几个名词。出题者应把整批 prompt 连续读一遍，发现节奏像模板或连续使用同一收尾时立即停下，使用受控的 `prompt-update` 流程更新 SQLite，并重新执行重复与机械质检；不能只把问题记为 `revise` 就继续发布。

末句需要单独横向比较。任何有实质内容的末句都不能在另一题中原样出现，也不能只替换少量词后重复。尤其不要批量追加“沿用现有启动方式”“补充测试并保证通过”“提供完整文档”一类与具体业务结果无关的尾巴。验收内容应按业务因果分散在正文中，结尾落到该题独有的业务结果、异常表现或使用者动作上。

“存储需要保存 A/B/C，再用 A/B/C/D 场景统一验证”也是固定模板，不会因为更换业务名词而变得自然。不要先堆功能，再把数据库、测试清单和运行环境集中塞在末尾；应写清失败时发生什么、谁能看到什么、恢复后如何继续。调度器要求每题提供 Docker 初始工程，但这项生产约束不能被机械复制成每道 User Prompt 的相同结尾。

### 技术栈多样性硬门槛

自动生成的 0-1 母题不能整批落到同一种语言、框架和数据库。5-7 题至少覆盖 3 种完整技术组合和 2 种主要编程语言；8 题及以上至少覆盖 4 种组合和 3 种主要语言。同一完整组合不得超过 40%，同一主要语言不得超过 50%，任一明确存储技术不得超过 60%。当前自动调度器只在 Go、Python、Node.js（JavaScript/TypeScript）和 Java 之间分配主要后端语言，不得生成前端任务，也不得使用未允许的后端语言规避比例限制。

多样性必须落到真实工程差异：运行时、框架、持久化、消息机制和部署方式要与业务相符，不能只改 metadata，也不能用同一种服务骨架替换库名冒充变化。技术信息写入 `languages` 并由仓库内容佐证。只有用户明确要求整批固定技术栈时，内部 spec 才可使用 `technology_policy: "fixed"`，并在 `fixed_stack_reason` 记录该要求。

## 初始快照

快照仓库只能包含完成该项目所需的上下文。README、设计说明、领域约定、注释、文档字符串、示例数据说明和用户界面文字应使用中文；包名、API、协议、命令、路径和代码标识符保持其正常写法。第三方许可证及工具自动生成且不适合翻译的文件可以保留原文。

文档应直接说明项目的领域、已有约束、目录职责、配置方式或运行方式。不得出现以下内容：

- User Prompt 原文或其拆解、验收清单、隐藏答案和实现提示；
- “本题”“任务执行者”“起始工作区”“初始脚手架”“待目标模型实现”等出题口吻；
- 评测、测评、标注、满意度数据、目标模型、答题模型、Coding Agent、Claude、Codex、benchmark、evaluation、质检报告或难度依据；
- 与项目无关的生产说明、内部审计字段、批次号和交付流程。

发布前逐个查看 `git ls-files` 返回的文件。机械质检给出的文件路径和命中词是最低门槛；即使没有命中，也要从读者视角确认文档像一个真实项目的初始仓库，而不是为了让某个模型答题而准备的材料。

## 证据

每个关于题目质量的结论都要落到可复查的信息上。Prompt 的复杂度依据应对应正文中的状态、并发、持久化、时间、恢复或集成边界；快照结论应引用具体文件和实际内容；仓库结论应引用本地 HEAD、远端分支 SHA 和可访问的 commit permalink。不能用“看起来真实”“不太像模板”代替证据。
