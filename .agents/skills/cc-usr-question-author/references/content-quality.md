# 题目与快照内容要求

## User Prompt

User Prompt 是交给开发者的一段真实需求，不是出题模板。正文必须使用自然、克制的中文书面语，并在同一段中交代业务处境、需要解决的问题、关键边界和可观察的验收结果。技术名词、协议名、代码标识符可以保留英文，除此之外不要用中英文逐句对照。

先从这道题独有的业务矛盾或使用场景起笔，再按事情本身的因果关系展开。不要以“从零构建一套”“请实现以下功能”等批量出题常用句开头；不要使用“背景：”“功能：”“技术：”“验收：”标签、标题、编号清单或相同的收尾句。不同题目不能只替换业务名词、技术栈和状态名后沿用同一语序。

需求中只出现使用者真正会关心的产品行为。不得提及数据生产、评测、标注、目标模型、满意度、题目难度、预期得分、轨迹、质检或“为了测试能力”等内部目的。验收标准写成可观察的业务结果，不写给评分人员看的提示。

## 初始快照

快照仓库只能包含完成该项目所需的上下文。README、设计说明、领域约定、注释、文档字符串、示例数据说明和用户界面文字应使用中文；包名、API、协议、命令、路径和代码标识符保持其正常写法。第三方许可证及工具自动生成且不适合翻译的文件可以保留原文。

文档应直接说明项目的领域、已有约束、目录职责、配置方式或运行方式。不得出现以下内容：

- User Prompt 原文或其拆解、验收清单、隐藏答案和实现提示；
- “本题”“任务执行者”“起始工作区”“初始脚手架”“待目标模型实现”等出题口吻；
- 评测、测评、标注、满意度数据、目标模型、答题模型、Coding Agent、Claude、Codex、benchmark、evaluation、质检报告或难度依据；
- 与项目无关的生产说明、内部审计字段、批次号和交付流程。

发布前逐个查看 `git ls-files` 返回的文件。机械质检给出的文件路径和命中词是最低门槛；即使没有命中，也要从读者视角确认文档像一个真实项目的初始仓库，而不是为了让某个模型答题而准备的材料。

## 证据

每个关于题目质量的结论都要落到可复查的信息上。Prompt 的复杂度依据应对应正文中的状态、并发、持久化、时间、恢复或集成边界；快照结论应引用具体文件和实际内容；仓库结论应引用本地 HEAD、远端分支 SHA 和可访问的 commit permalink。不能用“看起来真实”“不太像模板”代替证据。
